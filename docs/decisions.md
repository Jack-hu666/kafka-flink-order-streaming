# 关键设计决策记录（订单实时流处理）

## 决策 1：为什么用事件时间而不是处理时间

- **处理时间（processing time）**依赖数据到达 Flink 的时刻，而数据可能因为网络抖动、Kafka 分区不均、下游背压而乱序到达。用它开窗，同一批业务订单会因「到达早晚」被划进不同窗口，结果不可复现。
- **事件时间（event time）**用订单真正发生的时间（消息里的 `ts`）开窗，无论何时到达，同一分钟的订单永远落在同一个窗口，结果可复现、语义正确。
- 代价：必须配合**水印**处理乱序（见决策 2）。本项目 producer 故意制造 5% 乱序，就是为了验证这一点。

## 决策 2：水印设 5 秒的依据

- 水印是「允许事件迟到多久」的承诺：`watermark = 最大事件时间 - 5s`，窗口在水印越过窗口终点时才触发计算。
- 乱序程度：producer 制造的乱序是「比上一条小 1~10 秒」，实际乱序延迟集中在几秒量级。
- 权衡：水印越大，容错越强，但结果延迟越高；越小，延迟越低，但会漏掉迟到数据。
- **5 秒**是在「覆盖绝大多数乱序」和「结果端到端延迟可接受（秒级）」之间取的平衡点。若把水印降到 0，1% 的乱序事件会被直接丢弃；提到 30 秒，结果就要晚 30 秒才出来。

## 决策 3：为什么 3 个分区，和 Flink 并行度的关系

- Kafka 分区数 = 消费端并行度上限：一个分区在同一时刻只能被一个消费者（一个并行度实例）读取。
- 设 3 个分区，Flink 源并行度设为 3，就能 3 路并发消费，吞吐最大化；分区再多而并行度跟不上，是浪费。
- 本项目单机演示、数据量小，3 分区足够；生产上分区数要按「目标吞吐 / 单分区吞吐」反推。

## 决策 4：重复 order_id 怎么处理（本项目没去重，为什么、后果是什么）

- producer 故意制造 1% 重复 order_id，用来暴露「不去重的后果」。
- **本项目没做去重**，原因：
  1. 演示重点是「水印 + 窗口 + 容错」，去重需要引入额外状态（KeyedState 记录已见过的 order_id）和额外时延；
  2. 业务上 GMV 等聚合对偶发重复不敏感（1% 重复对 GMV 的误差约 1%）。
- **后果**：`order_cnt` 和 `gmv` 会被重复订单多算一次，是「近似正确」而非「精确去重」。若要精确，需按 `order_id` 做去重（如 Flink 的 Deduplicate + State TTL），并额外考虑状态大小与内存。这个权衡本身就是要能讲清楚的点。

## 决策 5：exactly-once 端到端能否做到，实际用的是哪种语义

- **端到端 exactly-once 极难**：它要求「Kafka 源 → Flink 状态 → 结果库」三段都 exactly-once，任何一段断开都做不到。
- Kafka 源支持 exactly-once（幂等 producer + 事务），Flink checkpoint 能保证**状态**的 exactly-once，但落到 PostgreSQL 的 sink 要 exactly-once 得用事务型两阶段提交（Flink 的 TwoPhaseCommitSink），复杂且吞吐下降。
- **本项目实际语义是 at-least-once + 幂等写入**：Flink checkpoint 保证故障恢复后不丢数据（at-least-once），结果表用 `ON CONFLICT (window_start)` 的 upsert 保证重放不产生重复行（幂等）。这样「重启后结果正确」而非「严格 exactly-once」。
- 这也是 README「局限性」一节要诚实写明的点：单机、at-least-once、无补历史机制、无 schema 演进。
